## 2 项目介绍

### 2.1 项目目标

本项目预期制作一个 Web 平台，允许测试人员将需求和接口文档上传，借助 LLM 生成测试点和用例，人工审核后对授权 HTTP API 发送真实请求，由平台按固定断言判定通过或失败并保留证据；失败时模型根据结果给出初步分析，由测试人员确认是不是缺陷；修复后可用同一测试任务清单/用例回归；并且能在干净环境里重放。

平台的定位是“LLM 辅助”，不是“LLM 自动测试”。模型负责读文档、提测试点、写用例、解释失败；是否通过由平台的断言代码判定；用例能不能入库、能不能执行，由测试人员审核决定。原因在于模型输出不稳定，不能拿它当最终判据。

项目最终实现以下三点算达成：

1. **功能**：B01–B08 逐项有可核对的结果，至少有 12 个获批有效用例，在正确基线和 4 个变体上实际执行，缺陷确认和同用例回归能连起来。
2. **性能**：B-P01–P05 在 4 vCPU、8 GiB 环境下达到教师拟定门槛。
3. **交付**：按课程要求第 3 节交齐项目计划书、需求规格说明书、系统设计文档、测试计划、测试报告、源码、可运行发布版、部署恢复说明、结项报告和过程记录；冻结版能在干净环境启动并复验。

### 2.2 项目范围

本期做：

- **项目与文档**：建立项目，保存需求文档和接口文档的多个版本，能查历史版本和两版差异，能指定本轮测试的目标版本。
- **用例资产**：用例库按“模块 → 测试点 → 实现”组织；测试点和实现都可修订，修改追加新修订，删除改为废弃；所有写入走变更集，人工审核后合并。
- **AI 辅助**：模型读文档，提出模块、测试点和候选用例；可以按文档差异或人的指令提出修订。每次任务记录模型、提示版本、日期和人工修改，产出必须经人审核。
- **任务清单**：为每一轮测试建清单，指定目标软件版本，选入已批准用例；清单从草稿到锁定单向变化，锁定时固化内容指纹；回归从上一份复制，支持固定修订和按新版本重新解析。
- **执行与证据**：填写执行环境（地址、初始变量、超时），逐条发真实 HTTP 请求；区分业务成功、业务拒绝、超时和连接失败；保留实际响应、错误信息和逐项判定；测试后可清理本组数据。
- **分析与回归**：模型对失败给出分析，测试人员确认是产品缺陷、用例错误还是环境问题，并写判断依据；缺陷报告含预期、实际、复现步骤、版本环境和证据；同一用例在缺陷版和修复版上分别执行，两次结果可追溯。
- **界面与部署**：提供浏览器端页面，覆盖项目、文档、用例库、AI 任务、变更审核、任务清单、执行记录和结果；提供部署、健康检查、数据初始化和恢复说明。

本期不做：登录与权限、成员分配、发布里程碑管理、手工修改结果、AI 直接判定缺陷、移动端适配、基线与标签、多条发布线、变更集逐项合并、逐行评论、并发冲突自动解决、跨任务记忆、运行中追加指令、AI 给用例评分。被测对象仅限教师授权的 HTTP API，覆盖 GET、POST 及合同约定的更新、审批或取消操作。

## 3 项目过程定义

### 3.1 过程模型：增量迭代

本小组选择增量迭代过程模型。

具体分两轮：

- **第一轮（W9–W11）基础执行版**：先把“项目/文档 → 用例审核 → 任务清单 → 真实 HTTP 执行 → 确定性判定 → 留证”这条主链路跑通。模型可以先只做最小验证，甚至用人工准备的用例，重点是把执行和证据做扎实。
- **第二轮（W12–W15）模型辅助与缺陷回归**：接入真实模型的测试点/用例生成、失败分析、人工缺陷确认、同用例回归；在基线、4 个变体和配对目标上实际执行；再测性能、练恢复，形成候选版。
- **收尾（W16–W18）**：核对制品、冻结版本、两场验收。

两轮都留一个可运行、可演示的版本。第一轮即使不接真实模型，也能演示“审核 → 执行 → 判定 → 留证”；第二轮再把模型接进来。这样模型服务出问题时，基础执行还能用，不会完全停用。

两条设计基线在 W9 定稿：

1. **断言判定由代码负责，模型只进行生成和解释。** 用例是否通过、产出是否合法、引文是否真的在文档里，测试结果是否真的正确，都由人工审核和确定性代码判断。
2. **写入走变更集，历史不可改。** 测试人员和 AI 的修改都形成变更集，批准后合并；修改追加新修订，删除改为废弃；执行结果绑定“实现 id + 修订号”，并附执行时的内容快照。

阶段顺序由平台代码固定，Agent 只在阶段内循环，不允许自己决定先做哪一步。这条是为了保证人工审核关卡不会被跳过。

### 3.3 方法与工具

- **契约先行**：模块之间传递的对象先定在 `models/`（pydantic）；用例库、文档与追溯、执行与历史三个领域模块互不 import，组合逻辑放工作流和 API 层。
- **代码组织**：按 `6-ModulePlan.md` 的 WP0–WP6 拆分；每个模块只把 `__init__.py` 导出的内容当公开接口；存储共用一个 SQLite 文件，连接从外部注入。
- **版本管理**：Git feature branch + PR；小步提交，提交信息写清模块和目的；`main` 保持可运行，每周打 tag。
- **测试**：单元测试用 unittest，不能调真实 LLM 或访问网络；假 LLM 测 Agent 循环；真实模型另写冒烟脚本；被测服务用 `fixtures/target_app.py`（学习者 CRUD，5 个可开关缺陷）。
- **AI 使用**：记录模型、提示版本、日期和 token；AI 产出先校验再人工审核；结项时提交 AI 使用说明，写清用途、采纳/修改和独立验证方式。
- **项目管理**：每周组内检查，更新周报和看板；M2、M4 各做一次匿名互评；设计评审至少两人参加并留记录。
- **工具**：GitHub、Classmoji、VS Code、uv、SQLite、FastAPI、React/Vite/Ant Design。

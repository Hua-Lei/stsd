# 文档导览

docs/ 按内容的变化速度分层，越靠上的文档越稳定，越靠下的越常改动。新增一条设计信息时，先判断它属于哪一层再落笔。

| 层 | 位置 | 回答的问题 | 变化频率 |
| --- | --- | --- | --- |
| 需求 | [prd.md](prd.md) | 平台要解决什么问题，为什么需要测试点这一层 | 很低 |
| 用户目标 | [use-case-analysis.md](use-case-analysis.md) | 用户用例分析 | 低 |
| 模块划分 | [domain-model.md](domain-model.md) | 有哪些模块，各自负责什么，谁依赖谁 | 低，只在模块边界改变时修改 |
| 跨模块契约 | [contracts/](contracts/) | 多个模块共用的形状：实现声明、事件载荷 | 低，改动是破坏性变更 |
| 模块规格 | [modules/](modules/) | 每个模块的接口、状态规则、错误与读模型契约 | 中，随对业务的理解加深而变化，影响范围限于单个模块 |
| 决策记录 | [decisions/](decisions/) | 某个设计为什么这样定，否决了什么 | 追加新记录，已写的记录只改状态 |
| 当前状态与计划 | [STATUS_AND_ROADMAP.md](STATUS_AND_ROADMAP.md) | 代码库现在到哪了，接下来做什么 | 高 |

模块规格里的 `CreateUser(...)`、`get_user_projects(...)` 是业务操作名，不是 Python 调用形状。

判断一条信息该放在哪一层，可以看它改变时会牵动谁。如果修改某个模块的内部规则会迫使你去改模块划分，说明这条信息写在了过高的层次。

## 约定与实录

docs/ 只放**约定**：别的模块和将来的代码必须遵守的东西。它写在代码外面才有意义，因为它约束的是还没写的东西。

描述代码现在是什么样的**实录**不进 docs/，它贴着代码写——模块的 docstring 里。实录放在 docs/ 里是纯粹的失同步风险：代码一改它当天就错，而没人会想起来回来改它。`modules/result_temp.md` 是这件事已经发生过的样子，它引用的 `Workflow` 模块已经不存在了。

一个文档如果需要标"同步记录"，说明它放错了位置。

## 一个事实只有一个家

重复是失同步的唯一来源。同一个事实出现在两个文件里，改一次就要改两处，而第二处迟早被忘掉。

所以：模块规格写自己的契约，不复述依赖关系；[domain-model.md](domain-model.md) 写依赖关系，不复述契约内容；多个模块共用的形状进 [contracts/](contracts/)，各模块链过去；决策记录写理由，不复述规则；实现状态只在 [STATUS_AND_ROADMAP.md](STATUS_AND_ROADMAP.md) 里。错误码目录属于 `errors.py`，模块规格只写别的模块真的依赖的那几条区分。

## 决策记录怎么写

只写两件事：当时在回答什么问题，否决了什么方案以及为什么否决。不要写当前设计是什么样——那是模块规格的事，写进来就会在设计变化时从"记录"变成"错误的指令"。

被否决的方案仍然是被否决的，理由还在，所以这样的记录不会过期。需要翻案时追加一条新记录，把旧记录的状态改成"已被 NNN 取代"，这是唯一允许对已写记录做的修改。

`decisions/` 不是实现依据。实现只看 `modules/` 和 `contracts/`；`decisions/` 只在问"为什么是这样"的时候读。

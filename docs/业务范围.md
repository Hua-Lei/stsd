# 结合大语言模型的全流程测试平台 · 业务范围

版本 v1.0　日期 2026-11-15　适用阶段：课程项目本期

本文只划业务范围，不展开技术方案与接口细节。

## 一、文档说明

本文说明本期平台做哪些业务、覆盖到哪一步、哪些刻意不做，供项目组统一口径，也作为课程评审的依据。"本期"指课程项目这一阶段交付的内容。

## 二、平台定位

团队依据需求文档和接口文档或代码源码对持续演进的软件做测试。如果缺乏统一的平台管理的话，需求文档会改版，软件会发新版本，但测试资产可能散落在个人经验、表格和一次性脚本里：当需求发生变化，可能难以判断哪些测试失效；结论只有"跑过了"，没有能回看的证据。

平台预期能够让个人或团队借助大模型对测试资产进行建立、长期维护，并确保测试用例的适用性。它把模型放在生成和解释的位置：模型读文档、提出测试点、写出可执行的请求与断言并解释结果；判定由平台按固定规则完成，入库由人审核决定。模型不适合做最终判定，同样的输入可能给出不同结论，也会把不存在的问题说得很像真的，所以"通过"必须能追溯到具体断言和具体修订。

## 三、本期范围内的业务

### 3.1 项目与文档

项目是最大的容器，记录被测软件、它的文档、当前版本，以及围绕它产生的全部资产和记录。所有对象都挂在项目下，界面顶部始终显示当前项目。

文档分需求文档和接口文档两类，各自保存多个版本。新版本只追加，旧版本不修改；平台提供两个版本之间的文本差异，作为后续修订的依据。

### 3.2 测试资产与修订迭代

用例库设计为长期状态，按树形组织：模块是文件夹，测试点挂在模块下，用例挂在测试点下。测试点是一个可以被断言回答的命题，说明测什么，不关心具体做法；用例是验证这个命题的一种具体做法，写清输入、步骤、预期和判定。一个测试点可以有多条用例。提取测试点时还要判断这条需求能否被观察和验证，不能测的要说明原因，而不是硬造用例。

测试点和用例都支持修订与版本迭代，这是本期资产维护的核心。资产进入用例库后，修改不是覆盖：每次修改追加一个新修订，旧修订仍然可读、可引用；删除是把状态改为已废弃，因为执行记录和审核记录还引用着它；移动只改变父节点，编号不变。历史可以查看，但不提供"一键恢复到旧版本"，要回到旧内容就提交一个新变更，历史始终是单向的。每条修订记录作者、时间和说明；本期作者只记为人或某个 AI 任务，不做身份认证。

写入只有一条路径：人和 AI 的修改都形成变更集，批准后合并。AI 提交的变更集必须经人批准才生效；人在界面上的新增和修改也走变更集，作者记为人。变更集整体生效或整体不生效，不提供逐项合并。

### 3.3 AI 辅助与审核

AI 以任务的形式参与，本期有三类：规划（读文档，划分模块、提取测试点）、生成用例（为已批准的测试点写用例）、修订（按文档差异或人的指令提出新增、修改、废弃）。每次任务有明确目标、可用操作、校验规则和轮次上限；它不能直接修改用例库，只能提交待审核的变更集。阶段顺序由平台固定，先规划、审核，再生成用例、审核；人的补充要求可以在每轮任务开始前、两次任务之间提出，运行期间不中途追加指令。

平台在提交审核前做校验：产出格式是否合法，测试点的引文是否真的出现在文档里，用例的请求是否与接口文档相符。不通过就把具体错误交回模型修改。校验通过后形成待审核变更集，人看摘要、校验结果和逐项差异，做一个整体决定：批准并合并，或拒绝并写理由。被拒绝的提案保留原状，可以带着理由新建修订任务。

AI 每次工作的上下文都从用例库和文档现取，不依赖跨任务的对话记忆，因此资产要提供标题一类能说明"这条在测什么"的描述，而不是只给编号和修订。

### 3.4 任务清单

每次测试不一定跑全部用例，全量跑成本高，修一个缺陷后也没有必要全量测试。所以可以为每一轮测试制定一份任务清单，说明这次要验证哪些用例、针对哪个软件版本，清单是执行的实际编排单位。

新建清单时填目标软件版本（必填）；名称选填。草稿可以人工勾选，也可以让 AI 先推荐再由人增删；AI 同样只用"添加"和"移除"来组建，不整单生成。清单只收已批准的用例，不允许同一用例的多个修订共存，条目顺序就是执行顺序。添加时一般不必指定修订，确有需要用旧修订验证新结构时可以显式指定，该条会标为"指定修订"提醒审核。

清单从草稿到锁定是单向的。锁定时校验清单非空、引用的修订可取，然后固化内容指纹；锁定后内容与条目修订不可改，名称可以改。

修订按目标软件版本解析：在该用例的目标软件版本的所有修订中取最新的修订。回归不重新编清单，而是从上一份复制：固定修订模式逐条保留原修订，适合原样重跑；重新解析模式保留用例集合、按新目标版本重新解析，是常规回归的默认，且必须在复制这一刻完成解析并写进草稿。补测分析还要读上一份清单测了哪些用例、结果如何；但上次通过不能直接推出本轮免测，判定条件是修订相同或内容未变且通过。

### 3.5 执行与结果

从已锁定的清单发起执行，填写执行环境：环境名称、被测服务地址、初始变量、单请求超时。初始变量用来放鉴权 token 之类的东西，界面默认遮蔽。执行时平台锁定每条用例的修订，逐条运行并把结果写入测试结果对象；结果只写一次，附当时的用例内容快照，之后用例被修改，历史结果仍然能对应上执行时的样子。

结果页先给汇总：通过、失败、错误各多少；点开某一行看证据：预期与实际、请求与响应、变量提取、用例快照。失败只表示证据与断言不符，不直接写"发现产品缺陷"。从结果页可以复制清单做回归，再次执行生成新的执行记录，不改写旧结果。

被测对象本期限定为可通过 HTTP 访问的服务，其他协议或客户端不在范围内。

### 3.6 网页端界面

平台是网页端应用，用户通过浏览器访问，不需要安装客户端。界面包含项目入口、文档、用例库、AI 任务、变更审核、任务清单、执行记录等页面，覆盖上面各节的全部操作。桌面浏览器优先，窗口变窄时可用，不承诺移动端适配。

## 四、本期不做

以下能力明确不在本期范围：成员分配、登录与权限、发布里程碑管理、独立报表菜单、手工修改结果、AI 给用例评分都不做；手工把失败改成通过会破坏结果的可审计性，所以没有这个入口。平台不承诺自动找出产品缺陷，失败只表示证据与断言不符，AI 对失败原因的归因不在本期。

其他不做项：基线与标签、多条发布线、变更集的逐项合并与逐行评论、并发冲突的自动解决、独立的环境管理页、清单拖拽排序、跨任务记忆、运行中追加指令、被测对象除 HTTP 服务以外的形态、移动端适配。

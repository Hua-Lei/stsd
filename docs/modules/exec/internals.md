# 执行器内部设计

> 本文是当前的设计形态，不是对外契约。它是临时落点：执行器实现之后，这些内容移进 `stsd.exec` 的模块 docstring，本文删除——描述代码现状的文字贴着代码才不会失同步。

## 四个部分

队列表、worker、容器端口、平台适配器。没有独立的调度器，调度收进了领取查询。

队列表一个任务一行，状态从待领取到执行中到终态。worker 数量固定，每个自己循环"领取、执行、写结论"，空闲才领。这样不存在容量协商，也不需要背压机制——所有 worker 都忙时，队列里的行就在那里等着。并发上限写进领取查询的条件：全局一档，按项目一档，后者是因为被测的是真实 API，同一个项目上无节制并发会把结果本身搞脏。

领取要带租约，执行期间心跳续租，过期的行重新变成可领取。理由见 [decisions/009](../../decisions/009-execution-work-unit.md)。

当前 `STSD_DB_URL` 默认是 SQLite，没有 `FOR UPDATE SKIP LOCKED`，写入也是单写者，所以第一版是单 worker 轮询。要多 worker 并行领取先换 Postgres，不在 SQLite 上手搓抢占。

## 容器复用

worker 领到任务后，把各修订的实现按**环境签名**（平台 `kind`、python 版本、规范化后的依赖集合）排序，然后顺序执行，手上保持当前这个容器，签名变了就销毁重建。

这等于一个容量为 1 的池，但不需要淘汰策略、容量上限和空闲回收。排序是关键：不排序时 A/B/A/B 交替会让单容器反复重装依赖，排完序之后同环境的修订连续，容量 1 就是最优复用。以后引入任务内并发再扩成多槽。

不跨任务保活容器。保活要管生命周期，还要承担任务之间的状态污染风险，而收益主要在依赖安装那一层，挂一个共享的 pip/wheel 缓存目录就能拿到。缓存产物，不缓存容器。

共用容器时每条修订一个新建的工作目录、一次独立进程，跑完删掉。单条修订有自己的超时并强杀；杀不掉就丢弃这个容器换新的，不要让一条卡死的修订把同环境的其他修订一起拖没结果。某个环境建不起来，该环境下的修订记 `not_run`，其余照常跑。

## 两个端口

容器端口只管沙箱生命周期、文件进出、执行命令并返回退出码和输出，完全不知道 pytest 存在。平台适配器知道 pytest：用哪个镜像、依赖怎么装、目录怎么摆、入口命令怎么拼、产物怎么解析成修订级结论。装依赖是平台适配器发出的一条命令，不是容器端口的能力。

这条缝让两个方向的变化互不影响：加一个平台只写新的平台适配器，把 Docker 换成本地子进程只写新的容器实现。后者正好是测试里最有用的那个——不起容器就能跑完整条执行链。

端口定义在执行器自己的 `ports.py`，实现在它的 `adapters/`。基础设施归属于需要它的模块，没有单独的 infrastructure 模块。

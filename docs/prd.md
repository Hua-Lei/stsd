
# 概述

本项目定位为 LLM辅助的全流程Web API测试管理平台，完成以下过程模型：

**录入需求和接口说明 → 模型生成测试计划/用例 → 人工审核修改 → 真实调用授权 API → 自动判定成功/失败并留证 → 模型辅助分析失败 → 人工确认缺陷 → 同一用例回归复测 → 干净环境可复现。**

我们将其分为几个核心部分：

1. 用例生成与持久化
2. 用例审计
3. 测试计划的生成与执行
4. 测试结果分析与持久化

# 需求分析

## 用例分析

我们从两个核心“使用者”：
- 用户
- Agent
分析本项目的用例，与其得出的基本的项目内提供的领域对象。

从*用户*角度来看，其首先管理**本平台**的与**实际应用平台**的**同步**
*用户*需要提供
- 具体管理的项目，与本平台和项目的链接
- 请求测试的项目版本，以及项目版本对应提供的需求与接口等文档


当一个项目版本准备就绪时，*用户*在这个平台下管理操作平台内的核心资产：**用例库**

*用户*可能使用*Agent*，*Agent*根据当**前项目版本提供的文档上下文**，经过多轮的检查验证，在用例库下生成测试用例。

*用户*对生成的测试样例进行审计后，**该测试用例即进入不可变状态，供后续的追溯**，用户可以从当前的用例库中选取需要测试的部分样例列出 **测试计划/任务**，并执行测试，并**持久化**该次测试任务反馈结果。

*Agent* 可以结合上下文和反馈得出**结果分析**，供用户辅助

用户后续可能根据反馈结果推进到下一个版本，可能做**回归测试**，也可能复现**旧有的测试结果**

## 复杂性分析

下面针对上面用例的具体环节，列出几点需求引出的复杂性

### 需求到测试用例的gap

上游项目提供了文档上下文，涵盖需求与接口，但是实际在平台中执行的是若干实际测试用例/脚本。二者之间有较大gap，这引出深层的需求：
1. 测试用例需要达到接口测试场景的**高覆盖率**
2. 测试用例需要**可管理**
而让Agent每次由文档直接生成实现是低效的，所以需要引入**测试点**，作为需求&接口到用例实现的过渡。

具体地，用例库本身应该**可分层管理**，在版本更迭过程中，Agent生成管理的对象首先**在测试点的级别**上进行，而不是实现

### 测试点版本控制

由上面的分析，我们将用例库中聚合管理的对象转变为**测试点**。

测试点的版本控制涉及到过程模型的多个环节。

首先是项目版本更迭时，可能有破坏性改动，需要**调整测试点**，也可能出现测试点不变化，而其实现需要更改。
所以测试点需要跟随项目版本产生其自身的**历史树**。另外在一个项目版本下的可能有多次修订，这是更细粒度的历史。

另一方面，由于需要保存测试历史，所以一次**经审计的**测试点对应用例的测试，就应该作为快照**不可变**保留下来。
